# Идеи: что заимствовать из oh-my-pi TUI

Автор — ZCode (агент); файл — рабочий список идей на основе изучения
`packages/tui` (см. [oh-my-pi-tui-classification.md](oh-my-pi-tui-classification.md)).
Раздел A — применимо в проекте zskin сейчас; раздел B — паттерны для
собственных будущих проектов; раздел C — от чего сознательно отказался.

## A. Применимо в zskin (CSS-темы ZCode)

1. **«Стили композера» как серия тем.** Восемь встроенных форм поля ввода
   omp (`box`/`band`/`claude`/`pi`/`borderless`/`rule`/`field`/`rail`,
   `components/composer/`) переносятся в CSS один-в-один: `rail` — левая
   акцент-рейка `border-left` + заполненный фон на селекторе композера
   ZCode; `field` — заполненная поверхность с капами; `band` — верхняя
   полоса-статус; `box` — скруглённая рамка со статусом в границе.
   Это готовая матрица визуальных вариаций для первого настоящего релиза
   тем zskin — не выдумывать с нуля, а транслировать проверенные силуэты.
2. **Генератор акцентных цветов сессий.** Алгоритм `theme/session-color.ts`:
   хэш имени → OKLCH hue, гамма-ограничения, проверка WCAG-контраста,
   минимальная дистанция от базового акцента. В zskin применим в
   генераторе тем: если хочется различать воркспейсы/задачи цветом,
   hue считает Python-генератор при сборке темы (CSS сам хэшировать не
   умеет), в тему зашиваются готовые значения.
3. **Тировая палитра для метрoв контекста/квот.** `chrome/context-thresholds.ts`
   задаёт уровни normal/warning/purple/error с тонами. У ZCode есть свои
   метры (`--color-usage*`, `--color-context-breakdown*` в рендерере) —
   тема zskin может перевести их на согласованную тировую шкалу вместо
   случайных цветов. Идея: палитра из 4 тиров как отдельный блок в теме.
4. **Shimmer-анимация по правилам omp.** `theme/shimmer.ts`: трёхтинговая
   палитра (low/mid/high), скорость в ячейках/сек, режим KITT-сканера.
   В CSS переносится как keyframes с градиентом на индикаторах стриминга
   (`data-zcode-stream-animate`) — живее стандартного пульсатора, дёшево.
5. **«Quiet mode» — приглушение tool-активности.** У omp есть
   display-preferences (hideToolActivity) и `ToolActivityContainer`.
   CSS-эквивалент для zskin: тема, которая не скрывает (принцип 2 —
   скрывать нельзя), но визуально затухает блоки инструментов
   (opacity/шрифт), оставляя полноценными сообщения и подтверждения.
6. **Дисциплина семантической палитры.** В omp всего 45+ именованных
   токенов с разделением fg/bg и маппингом «токен → тон» (`native/tone.ts`).
   Правило для тем zskin: тема описывается маленьким набором семантических
   значений (фон/панель/граница/акцент/роли/терминал), а маппинг на токены
   ZCode (`--color-*` из ui-tokens-3.14.3.txt) — механический. Это спасает
   от «раскраски ad hoc» и переживает смену версий.
7. **Прогрессивное сворачивание как принцип оформления.** omp сворачивает
   всё небезопасно-длинное (thinking по Ctrl+T, tool-вывод по Ctrl+O,
   лимиты 3000 строк с tail-обрезкой). Для zskin: стилевой паттерн
   «collapsed по умолчанию» — компактные превью-строки с явным
   expand-хинтом (у ZCode для этого есть `data-state`/collapsible-хуки).

## B. Паттерны для собственных проектов (TUI/CLI)

1. **Двухслойный вывод (ANSI + семантика).** Контракт «рендер в строки +
   опциональный `describe()` в семантическое дерево» (`native/node.ts`)
   — способ дать одному UI и fallback-терминал, и нативные виджеты без
   форка логики. Самый ценный архитектурный приём пакета.
2. **Минималистичный контракт компонента.** `render(width) → readonly
   string[]`, где неизменённый компонент возвращает **тот же массив**
   — дешёвая мемоизация по reference equality; `invalidate()` для сброса.
   Проще React-модели и достаточно для TUI.
3. **Diff-reconcile для семантических деревьев.** `native/reconcile.ts`:
   diff по id, keyed reorder → move-операции, «settle» зафиксированных
   блоков (`native/settle.ts`) — паттерн для любого стримингового UI,
   где хвост живой, а голова заморожена.
4. **Декларативный статус-лайн.** Сегменты с `render()`/`describe()` +
   реестр + пресеты + сепараторы + лэйауты под форму ввода
   (`status-line/`). Хорошо масштабируется и конфигурируется; брать как
   референс архитектуры, не как код.
5. **Registry-паттерн для стилей.** `registerComposerStyle()` с
   disposer'ом, защитой builtin'ов и fallback'ом — универсальный способ
   дать расширениям точку входа в оформление.
6. **Оркестратор автодополнений.** `prompt/prompt-action-autocomplete.ts`:
   один провайдер, приоритет триггеров (`/`, `^`, `#N`, `:`, `scheme://`),
   плюс `prose-gate.ts` — фильтр «проза vs код/путь» перед spelling/
   подсказками. Редкий по качеству UX-слой для терминального ввода.
7. **OutputSink со стриминговыми лимитами.** `tools/streaming-output.ts`:
   окно хвоста, лимиты строк/байт, spill в артефакты, head/tail/middle-
   обрезка — обязательный элемент для любого агента с длинными выводами.
8. **Адаптивный рендер-цикл.** Троттлинг от 30 fps до ~5 fps под нагрузкой
   (`loop-watchdog.ts` детектит блокировки event loop) + synchronized
   output (CSI 2026) + DECCARA-заливка фонов. Набор приёмов «TUI, который
   не тормозит и не мигает».
9. **Standalone-каркас одноразовых TUI.** `apps/standalone-picker.ts` —
  .lifecycle-фреймворк для селектора/промпта вне основной сессии; удобно
   для CLI-утилит внутри своего проекта.
10. **Debug-сервер TUI.** `debug-server.ts`: TCP-инспектор (дерево
    компонентов, paint, инъекция ввода) — идея для отладки собственных
    терминальных приложений.
11. **Онбординг с version-gating и живым превью.** `setup/`: сцены с
    `minVersion`, пропуск по env, mock-превью реальных компонентов
    (статус-лайн/редактор) при выборе темы/формы ввода.

## C. От чего сознательно отказываюсь

- **TSP/Glyph-протоколы** — зависят от узкого круга терминалов и
  APC-канала; для zskin неприменимы (там DOM), для своих проектов —
  только если появится реальный нативный хост.
- **Голосовой слой** (`live-visualizer`, push-to-talk, STT) и
  **collab-QR** — вне текущих задач.
- **Vim/kill-ring полной комплектации** — брать только при реальном
  спросе; это большой объём кода вокруг нишевой фичи.
- **Перенос оверлеев/приложений omp как есть** — у ZCode свои экраны;
  ценны только паттерны, не конкретика.
